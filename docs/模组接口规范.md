# PixelMC 模组接口规范 v1

生效规则：2026-11-06 起，PixelMC 新增或变更的模组、Manager 服务及 Hub 玩家接口必须依本规范设计、评审和检查。本文是可版本管理的长期准则，地位与插件页面风格规范相同；不是已完成全部改造的声明。用户的新决定应修订本文有效规则，并保留迁移记录。现有协议未迁移前继续兼容，不得借规范化删改既有玩家数据或行为。

本地候选已实现 Forge 1.20.1 排行榜 provider、可选食物书适配、三榜数据库投影、变化通知及原生页面，当前社区扩展候选版本为 Hub 0.5.0-dev 与 Manager 0.9.0-dev。检查覆盖本地构建、隔离 HTTP/SQL 和隐藏 GPU。服务器部署与用户实游验收待完成。文中“必须”描述接口准则，末尾迁移表描述实际源码范围。

## 1. 所有权与依赖

- 业务模组仍拥有自己的领域数据、规则与事务：MemorialTitles 拥有称号，DailyFortunes 拥有抽签/签历；第三方食物模组仍拥有品尝状态。Manager 统一身份、会话、管理、存储协调及可重建统计投影；Hub 是可选玩家读/明确授权操作与呈现端。
- Manager 的排行榜计数是源业务的派生投影/统计副本，不能把业务表搬入 Manager、对原业务表另建写入口，或用统计副本修复/覆盖源记录。备份、删除、撤权与重建规则必须随命名空间定义。
- 独立模组不得因为接入本规范而强依赖 Manager。可选发现失败时保留原独立运行路径；不因 Manager 离线另起第二套玩家身份库，不把失败静默切到另一数据库。Hub 缺少可选模块时明确 unsupported/unavailable。
- 正常链路为“游戏服务端在合法线程读取已有状态 → 有界桥接/后台持久投影 → Manager 后台展示与经授权的 Hub 读投影”。Hub 不直连数据库、不调用管理 HTTP/RPC、不持有管理令牌，也不从客户端上报的数值建立排行榜。

## 2. 身份与作用域

1. 玩家主键是规范小写 UUID。昵称、皮肤 URL、客户端 payload 中的 UUID 都不能代替连接身份。玩家请求中的本人 UUID 由已鉴权 Minecraft 连接取出，并在 provider 执行与返回前验证会话仍有效；假人和未准入玩家不得写档或借用真实玩家资格。
2. trusted-server 事件须来自已鉴权游戏桥接实例，服务端从真实玩家对象和既有准入结果取身份。后台必须核对连接对应的 server/scope，禁止客户端任意指定其他存档、服务器或玩家。
3. 统计键至少包含 `{providerId, capabilityId, playerId, scope}`。scope 显式声明 `kind: global|server|pack|archive` 及适用的稳定 `serverId/packId/archiveId`；不适用字段用 null，不从显示名猜测。archive 是稳定世界/存档身份，换世界必须隔离；pack 版本是元数据，不自动等同新 pack 身份。
4. global 表示已声明的业务全局域，不是可跨无关服务器/管理实例任意合并的互联网全局。公开 scope.id 是无秘密的投影键；真实访问仍由连接上下文约束。缺少权威 scope 时停用持久跨会话缓存/上报，不能生成临时随机 ID 后混入正式统计。
5. 玩家改名更新当前公开显示名，历史签文/操作快照不追改。存档复制、恢复、重置与换整合包的统计语义必须明确；不得只以同名世界目录当同一存档。

## 3. Provider、capability 与权限分层

新增发现描述至少包含独立的 `providerId`、`modVersion`、`providerVersion`、`capabilities[]`；每个 capability 具有稳定 ID、整数版本、audience、允许 actions 与请求/响应界限。modVersion 是发行版本，不能替代 capability 协议版本。例如：

```json
{"providerId":"pixelmcmanager","modVersion":"candidate","providerVersion":1,
 "capabilities":[{"id":"leaderboards.read","version":1,"audience":"public-summary","actions":["page"],"maxPageSize":100}]}
```

发现只是能力描述，**不授予路由或权限**。动态注册只能注册经过审核的 namespace/capability 与 handler；服务端及 Hub 各自保留 action+字段白名单，默认拒绝未知操作。不得自动扫描反射方法、枚举管理 RPC、转发任意 extension/method/SQL，或因某模块注册了写接口就让玩家调用。

| audience | 可接收内容 | 必须保留的边界 |
| --- | --- | --- |
| self | 本人明确信息及既有获准玩家操作 | 真实连接 UUID、所有权/可见性、显式 action；不接受任意目标 UUID |
| public-summary | 经业务批准可公开的最少排行摘要 | 仅 UUID、显示名、已批准头像、名次、聚合数值；不返回私有明细 |
| trusted-server | 服务端采集、已提交业务变更及投影同步 | 桥接身份、准入、scope、幂等/修订校验；不能直接暴露给玩家 |
| admin | 管理设置、删除、恢复等管理操作 | 既有管理员鉴权、CSRF、审计与权限；没有通往 Hub 的通用隧道 |

已有 Java 可选边界 `request(UUID,String,String) -> CompletableFuture<String>` 与 `protocolVersion()==1` 保持兼容。旧别名 manager/titles/fortunes/updates 不因命名空间标准化改名；新描述可映射 pixelmcmanager/memorialtitles/dailyfortunes 等 owner namespace。增加 capability 不提高旧 protocolVersion、不假称旧 peer 支持新能力；缺少协商时继续旧 v1 全量安全响应。

## 4. 字段、时间、空值和错误

- 新 JSON 使用 camelCase；ID 是字符串，日期为服务端指定时区的 `YYYY-MM-DD`，时间点为 Unix epoch **毫秒**，时长为非负**毫秒**，不用 tick 或未标单位的秒。revision 是不透明令牌，不能按字符串大小猜先后；事件另有 epoch/sequence。
- 计数是非负整数，Web 可见数值不得超过 JS safe integer。超界须显式协议升级/受约束字符串表示，不截断、溢出或取模。Food/fortune 单位在字段/契约中固定，不能把归档天数冒充不同签种数。
- 已知 0 是合法数值；missing/unknown 使用 null 并带相应状态；unsupported 表示能力没有提供，unavailable 表示能力存在但源、基线或连接暂不可用。不得把异常/超时/配置读取失败/初次登录未读到 capability 都覆写为零。
- 空列表只有在权限与完整查询已确认、total=0 时才是 empty。loading 不显示伪造的零总数；旧的已确认缓存若保留，必须与当前可用状态区分，不能替代当前鉴权。
- 错误需有稳定 code 与安全 message，至少区分 UNSUPPORTED、UNAVAILABLE、UNAUTHENTICATED、FORBIDDEN、INVALID_ARGUMENT、CONFLICT、RATE_LIMITED、TIMEOUT。管理员可在服务端按 requestId 追踪原因；玩家响应不泄露 SQL、JDBC、密钥、路径或堆栈。
- 请求和响应均先按 UTF-8 字节限长、检查 JSON 类型/深度/数组长度，再做业务处理。默认沿用 Hub 普通请求 8KiB、普通响应 512KiB 的较小边界；各 provider 更小限制仍有效。既有 updates 64KiB digest / 2MiB fragmented response 是显式协商例外，不能替别的模块自动放宽。

## 5. 写入、幂等、并发和通知

- 玩家写操作必须是审核过的具体业务动作与显式目标值，例如设置 equipped/visible，不能用重试不安全的 toggle。需要并发保护时传 expectedRevision；冲突返回当前修订，前端不乐观伪造成功。
- 可重试写入使用作用域化 operationId；同请求重发得到相同结果，不重复消费、计数或发放。不得为了缓存修复换 operationId 再做一次写入。实物/资格只能在源事务确认后消费，源业务仍是唯一裁决者。
- 变更事件仅在事务 commit 或明确内存权威状态切换完成后发出；事件携带 sourceEpoch、sequence、scope、受影响 capability/聚合键与 revision，尽量发小提示/增量，不发送完整私有业务记录。
- 订阅与响应绑定 session generation。退出、切服、换档、换玩家、重连或 capability 撤销后，旧 future/后台 IO 即使完成也不得写入新会话。传输 baseline 先按顺序推进，再丢弃已过时的 UI 回复；事件去重/合并不得破坏次序。
- 断线重连、epoch 改变、sequence 缺口、缓存校验失败必须执行一次有界 baseline/reconcile；不要因“以前账户下载过”假定本机持有内容。不可重放的缺口允许全量当前页/当前模块重建，但禁止新增周期全量扫描。
- 源重置、配置改变或历史修复可以令值下降，统计副本不得永远取 max。以源 epoch/revision 与显式重建处理旧事件，防止旧回调复活被撤销的成绩。

## 6. 线程、存储、缓存和容量

- Minecraft 对象只在合法服务器线程读取必要内存快照。JDBC、磁盘、网络、压缩、全量编码与昂贵统计放在有界 worker；不在 tick/render/login 线程等 future，不建立无限线程/队列。
- IO 线程数、队列、每玩家/连接请求率、超时、响应字节与批次数量必须声明。新的读取一般 10s 内超时，沿用旧 provider 可保持已有 20s 工作/25s 外层边界；不能无限等待或自动无限重试。重试由连接恢复、明确用户操作或已提交变更提示驱动，合并重复请求。
- 排行查询必须使用有索引、按 scope 的投影；事件增量/脏标记驱动更新。首次连接可做一次有界分批基线，缺口恢复亦同；不得新增每 tick、每次打开页面或固定周期扫描所有在线/离线玩家和全数据库的任务。
- 原数据库/表和备份归属不变。Manager 统计副本必须能从合法源重建，带来源/时间/修订；不得越权读取尚未批准的表。删除/撤权需同步 tombstone 或重建，使旧事件无法恢复已删除结果。
- 客户端历史缓存按 UUID + 权威 scope + capability/query/version 隔离，限制大小/数量，后台原子写入并校验内容 hash。缓存 hash 描述本机实际内容，不是账号“已下载”标记；重建后验证完整 root/order/deletion。
- 历史磁盘内容只有当前连接确认授权/可见性后才注入正式 UI。撤权、隐藏、删除必须撤下相关可见内容，缓存永不授权；不可缓存未解签结果、票据 token、管理数据或尚未批准的公开字段。scope 不同业务不同，不能把世界范围榜误按仅 serverId 缓存。

## 7. 首次用例：三项排行榜

| board | 页面指标与范围 | 权威来源/聚合要求 | 当前迁移状态 |
| --- | --- | --- | --- |
| food | 美食品鉴；archive，UI“本存档”；单位 foods | 食物书认可的有效已品尝种数。当前 solcarrot1.20.1-1.15.1 中 FoodCapability.getEatenFoodCount 是原始 set 大小，FoodList.getProgressInfo().foodsEaten 会按 shouldCount 过滤；必须复用与食物书相同语义，不能直接取原始 set。 | 已实现可选反射适配、事件采集及 archive 投影 |
| fortunes | 签笺收藏；业务 global；单位 fortunes | DailyFortunes 中 state=archived 的不同 fortuneId 数；相同签多天归档只计一种。现有 archiveCount 是归档记录条数，不能直接当本榜值；读取要由业务 owner 提供聚合。 | 已由 FortuneBackend 提供去重聚合，落业务 global 投影 |
| online | 在线时长；archive，UI“本存档”；单位 ms；仅累计 all | Manager 现有累计统计/pm_players.total_ms 可作来源；正式实现前核对 archive 关联与轻量当前会话 checkpoint，保留真实墙钟毫秒，不按 tick、不从网页时钟累计写库。 | 复用已接受的 pm_players.total_ms，按活动 archive 投影 |

食物流程必须覆盖：登录/连接先合法 baseline → 此后品尝变化/重置/配置变更更新；读取失败保留先前确认值并标 unavailable，不能覆零。数据库键以 UUID+稳定 archive scope 隔离。与其他模组的互通通过可选适配器完成，食物模组不必硬依赖 Manager。不存在的历史周统计不能从累计数倒推出周榜；首版不提供周榜或自动授予称号/奖励。

共享 Web 源位于 `PixelMCPlayerHub/src/leaderboards/{contract.js,demo.js,schemas/projection.schema.json}`，两页引用同一 DTO/fixture，不建立双份排行榜算法。公开行是 `{playerId,name,rank,value,rankDelta?,avatar?}`；viewer 是当前连接身份，self 可在当前 Top-N/页之外。不得附带吃过哪些食物、逐日签历、未解内容或任意 privatePayload。

核心字段：`schemaVersion:1, board, status, supported, period:'all', ranking:'competition', scope:{kind,id,label}, unit, rows, total, page, size, updatedAt, revision?, comparisonRevision?, viewer, self`。状态为 ready/loading/unavailable/unsupported/empty/error；self 的未知 value/rank 为 null，不能伪装0。avatar 只返回已批准同源公开路径+版本，复用现有头像缓存/默认素材，客户端不自行拼远程皮肤请求。

先在完整权威投影中按 `value DESC, playerId ASC` 稳定排序，计算 competition rank（1,2,2,4），再分页；相同分数名次相同，UUID只用于稳定次序。page 从0起，默认 size20、上限100；total 是过滤和scope后的全榜人数，不是当前页长度，self 不改变分页条数。真实多页必须绑定同一不透明 revision；修订变化时重新确认相关页，不拼接不同快照。前端不得自行对可见页排序/重算名次。

实时名次变化使用可选 rankDelta（有符号安全整数或null），正值上升、负值下降、0未变；首次无基准或该玩家上次未入榜时为null，旧v1缺字段仍兼容。顶层 comparisonRevision 指向**同board/scope前一次服务端已发布的完整排行快照**，不能取本机上次访问缓存、当前页或另一个scope。按 previousCompetitionRank-currentCompetitionRank 计算变化，再分页，不使用数组下标之差。数值delta必须有非空且不同的当前revision和comparisonRevision，当前rank及 previousRank=rank+rankDelta 都须为>=1的安全整数；self未上榜时delta为null，self与可见本人行的变化值必须一致。

后续真实数据链路在源事件commit后，经已有通知触发一次有界读取/补丁，将同revision的rows/self/total/comparisonRevision原子替换；丢事件或重连做baseline/reconcile，不能逐行混接两个修订，也不新增轮询或周期全榜扫描。本地 Manager 服务已实现完整发布快照与按榜变化令牌，经已有桥接响应传递，客户端使用同修订窗口原子更新。

Manager 管理读投影已接入 `GET /api/playerhub/leaderboards?instance=<id>&board=food&period=all&page=0&size=20`，沿用既有管理员会话。游戏 Hub 使用独立 `leaderboards.read` public-summary capability，玩家操作固定为 snapshot/page/aroundMe/window。模块缺失显示 unsupported，服务或来源故障显示 unavailable。正式后台与游戏连接使用权威数据。

演示数据只用于显式 Web 预览，生产依赖图必须排除模拟数据模块。

## 8. 兼容、合同检查与迁移记录

新增能力至少检查：不存在/关闭 provider、旧 v1 peer、未经授权目标 UUID/scope、字段白名单、null 与0、单位、并列跨页、重复请求、并发 revision、先 commit 后通知、丢事件后的 baseline、退出后的延迟回调、源值下降/重置、超时/满队列、坏缓存/不同电脑/撤权。各 loader/MC 适配层共享相同 golden DTO 与错误向量，按实际支持目标分别编译/检查；只通过 Forge 不能宣称 Fabric/NeoForge 已迁移。Web fixture 检查不是服务端鉴权/SQL或实游验收。

向后兼容新增可选字段、独立 capability 协商；不删除旧 v1 action、不改变已部署字段单位/含义、不重用旧字段表示新指标。必须破坏语义时新增 capability major，并保留旧适配/迁移窗口。shared Web schema 更新先协调两个消费页面；未知私有字段在公开 DTO 边界拒绝，不能自动透传。

### 8.1 排行榜候选的具体边界

- providerId 为 pixelmcmanager，providerVersion 为 1，capability 为 leaderboards.read v1。discover 附 descriptor，路由继续使用已审查的静态白名单。
- 登录先读取三榜各前 20 行。客户端按连接、本人 UUID、board/scope 保留至多五页窗口，退出清连接态。普通提示只标脏当前受影响榜单，打开并查看该榜时读取一次 window。首次预载与桥接准入竞态允许由提交提示触发一次有界补读。
- 提示由已有桥接 checkpoint 响应附带 food/fortunes/online 三个令牌，再发带 session 和位掩码的通知。服务提交后推进令牌。已有在线统计 checkpoint 继续使用真实墙钟毫秒。
- 每名玩家读取间隔至少 100ms。桥接合并 160ms 内同时到达的读取，每批至多 32 个，等待队列至多 128 个，同时执行一批。每项在发送前与回执后分别复核会话，服务逐项核对准入。内部 rankingsBatch 仅属于已鉴权游戏桥接。
- 常规 Hub 请求 8KiB、响应 512KiB。读取经现有有界 worker，bridge HTTP 4s、API 7s、外层 provider 8s 超时。失败等待后续提交提示或明确重试。
- ph_ranking_values 保存可重建数值，ph_ranking_boards 保存来源状态与发布修订，ph_ranking_published 保存名次、数值和完整序号。PlayerHub 原生存储清单升为 v2，共 11 表。三张新表进入完整备份及玩家删除/恢复流程。
- 按完整当前正值投影排名，0 保留为已知未入榜数值。历史食物值随该玩家下次登录或源事件补齐。食物模组缺失时只停用该来源，支持目标为 solcarrot 1.20.1-1.15.1；其它版本需检查 API 能力。
- 当前窗口绑定同一修订。服务保留当前、前次及前次的比较基准，过期页返回冲突并进行一次当前窗口对账。完整榜先计算 competition rank，再分页及计算本人位置。
- 源值下降、配置重载、foodlist 清空、签笺删除、玩家全局删除及恢复均需更新派生值。新连接和新 archive 分开处理，缓存只保存公开汇总。

### 8.2 社区资料候选的具体边界（2026-11-07）

- Forge 1.20.1 的 `community` provider 继续 Java protocol1，独立发现 `communityApi:1`，声明 public-summary 的 profile/memories/memory 与 self 的显式写操作。本人写入不接受目标玩家 UUID；其他玩家公开读取限于当前鉴权实例已有成员，只返回已选择的展示对象及公开回忆，私有获得候选仅本人或独立管理员接口可见。
- 名片沿用全局 UUID 身份与获得源，背景色/图案、语录及已获称号/归档签/已参与旅程选择存于 Manager。精选签仍使用 DailyFortunes 已注册 `featured_date`，与资料行在同一 Connection 事务中 CAS 保存。DailyFortunes 的新增方法仅为 Manager service 内部的只读公共投影，不改独立游戏模组或签筒行为。
- 原文限本人当前旅程编辑；历史使用幂等 operationId 补记，24h 内本人可删。管理员的任何年龄原文/补记编辑删除采用独立已鉴权 HTTP + CSRF + 审计路径；删除需当前 revision 与明确确认。删除 tombstone 不被旧 operationId 重试复活。
- 真实档案、成员、获得时间与历史原文缺失如实为空。options/档案每页100、补记每页20，服务端先完整筛选排序后分页，不将预览示例或编造日期导入正式源。来源已配置但不可用返回失败，不能冒充空集合。
- PlayerHub native manifest 升至 v3/15表，四张 `ph_community_*` 参加完整备份、空库恢复与全局玩家删除恢复。已提交变化通过现有 hello/checkpoint/bootstrap 的 `communityRevision` 和 Hub 提示失效；不增加社区轮询或周期全库扫描。输入8KiB、响应512KiB、本人请求至少100ms、外层API7s，退出后延迟回执复核原会话。
- Manager 正式 `hub-players`/`hub-history` 与预览共用展示组件但使用不同 data adapter。生产构建拒绝 community demo/adminPreview/browser store 依赖。列表六种排序、分类计数和分页来自真实SQL；冲突保留草稿，候选/补记及归档后页可达。
